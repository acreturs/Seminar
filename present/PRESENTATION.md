# PART A — How to read & build this file

## A.1 Golden rules (from `INSTRUCTIONS.md`, non-negotiable)

1. **Little text, many figures.** Bullets are speaking anchors, not sentences. Never read off the slides.
2. **Reveal everything step by step (progressive reveal).** Every slide is a *sequence of reveal steps* — not one finished block. This helps the audience locate where we are and forces one slide / 2 min with dense but controlled content.
3. **Respect the per-section time budget** (see A.4). Rehearse with a timer.
4. **Re-draw figures instead of screenshotting** where it improves the explanation (pipelines, diagrams).
5. **Avoid:** too much text, reading slides, dwelling on background, showing every experiment. Only the experiments that tell a *story*.

## A.2 Reveal convention (the core principle of this file)

Every slide is defined as **`▸ Reveal 1 … ▸ Reveal n`**. One reveal = one click / one animation.

- **Reveal 1** is always the minimal anchor (headline + one image/keyword). A slide never starts fully populated.
- Later reveals add **exactly one thought / element** each (a bullet, an arrow, an image half, an equation line, a table column).
- For pipelines: one stage per reveal, connected by **arrows**, earlier stages stay visible (dimmed).
- For tables: first show the method row empty/highlighted, then fly the numbers in; or column by column.
- Rule of thumb: **3–6 reveals per slide.** More → split the slide. Fewer → the slide is too static, check if an animation is missing.

## Slide 6 — The core idea: flow from renderings, not from noise · Method · ⏱ 2 min

**Takeaway:** FlowR learns a velocity field that flows **renderings of a (sparse) reconstruction → ground-truth images** — if the reconstruction is already good, the image stays ~unchanged (no hallucination).

**Reveal sequence:**
▸ Reveal 1 — Headline + **standard diffusion on top:** `p0(z) = N(0,I)` (pure noise) →[flow]→ `p1(z|y)` (data). Label: "invents everything → hallucination/inconsistency".
▸ Reveal 2 — **FlowR below:** the source is **conditioned on y**: `p0(z|y)` = renderings of the initial 3DGS reconstruction →[flow]→ `p1(z|y)` = GT-like images of a dense reconstruction.
▸ Reveal 3 — **the trick, justified:** fitting a 3DGS to few images = drawing from a stochastic process → **a rendering of `Gsrc` at pose `Ptgt` IS a sample from `p0(z|y)`**.
▸ Reveal 4 — **consequence (money sentence):** if a view is already good, the needed velocity ≈ 0 → the model **corrects** instead of inventing → sharper, consistent, no averaged hallucinations.

**Visual:** **paper Fig. 1** (standard vs. FlowR flow) — best re-drawn for clarity.
**Speaker note:** this is *the* slide. Draw the contrast noise→data vs. rendering→GT sharply out loud; tie back to the Slide-5 teaser.
**Source:** paper abstract, intro (l. 30–38), Fig. 1, Sec. 3.2; idea inspired by [32] "Flowing from words to pixels".

## Slide 7 — The pipeline in 3 stages · Method · ⏱ 2 min

**Takeaway:** Three stages: robust **initial reconstruction** → **flow-matching view enhancement** → **improved reconstruction** on the augmented view set.

**Reveal sequence:**
▸ Reveal 1 — Headline + empty pipeline skeleton with 3 boxes + arrows.
▸ Reveal 2 — **Stage 1 — initial 3D reconstruction (Sec. 3.1):** posed images → co-visibility graph (keyframes via FPS) → MASt3R matches → tracks → COLMAP triangulation → metric scale alignment (Metric3D v2) → short 3DGS fit (5k steps, ADC/AbsGrad). **Output `Gsrc`.**
▸ Reveal 3 — **Stage 2 — flow enhancement (Sec. 3.2):** render `Gsrc` at target poses `Ptgt` → multi-view flow model → **enhanced images `Itgt`** (20 ODE steps).

## Slide 8 — How the flow model learns (flow matching) · Method · ⏱ 2 min

**Takeaway:** Conditional flow matching on a straight optimal-transport path between rendering and GT — trained with a simple velocity-regression loss.

**Reveal sequence:**
▸ Reveal 1 — Headline + **ODE:** `dz_t = v(z_t, t) dt` (Eq. 4). Small sketch: straight path from `z0` (rendering) to `z1` (GT).
▸ Reveal 2 — **interpolation path (Eq. 5):** `z_t = t·z1 + (1−(1−σ_min)·t)·z0`, `σ_min=1e−5`.
▸ Reveal 3 — **target velocity (Eq. 6):** `v_t = z1 − (1−σ_min)·z0` — constant along the path (OT path).
▸ Reveal 4 — **loss (Eq. 7, CFM):** `L = E_{t,z0,z1} ‖ v_θ(z_t,t) − v_t ‖²`, with `z0~p0(z|y)`, `z1~p1(z|y)`, `t` from a logit-normal; `t` independent per frame (Diffusion Forcing → faster convergence).
▸ Reveal 5 — **inference (Eq. 9):** Euler steps `z_{t+Δt}=z_t+Δt·v(z_t,y,t)`, **only 20 steps**.

**Visual:** left half a straight-path sketch, right half the 4 equations revealed step by step. Annotate the conditioning `y=(Isrc, Ptgt)`.
**Speaker note:** don't drown in math — core message: *straight line, predict velocity, 20 steps*. Mention logit-normal/Diffusion Forcing only briefly.
**Source:** paper Sec. 2.2 + 3.2; Eq. 4–7, Eq. 9.

## Slide 9 — Architecture: multi-view DiT · Method · ⏱ 2 min

**Takeaway:** A text-to-image DiT is extended with multi-view attention → generates **N consistent views simultaneously**, conditioned on source images + camera rays; scales to **up to 45 views on a single H100**.

**Reveal sequence:**
▸ Reveal 1 — Headline + **backbone:** large T2I DiT (rectified flow, SD3-style), text layers removed → **1.6 B pretrained + multi-view layers → 1.75 B total** (pretraining preserved).
▸ Reveal 2 — **latents:** VAE-encode (dim 16), 2×2 patches → tokens + 2D pos-enc + **1D view-index encoding γ(i)** (index ~[0,1000] during training → variable/many views).
▸ Reveal 3 — **multi-view DiT block (Fig. 5):** first self-attn = exactly the image model; then a second **full multi-view self-attention** across all views; **zero-init linear** at the end → start identical to the image model. 24 blocks.
▸ Reveal 4 — **camera conditioning:** **Plücker ray maps** for source & target poses, in the frame of the most central camera; concatenated into the MV block.
▸ Reveal 5 — **scaling:** training 512px/12 views, finetune 960px/6 views; inference **up to 45 views @ 540×960 (91K tokens) in a single forward pass on 1× H100** (12 views ≈ 17 GB).

**Visual:** **paper Fig. 5** (DiT block) — re-draw, highlight the two self-attentions + zero linear.
**Speaker note:** message: cleverly *keep* the image pretraining and only *add* multi-view; multi-view attention = source of consistency.
**Source:** paper Sec. 3.2, impl. Sec. 4, Appendix A.2 + Fig. 5; Tab. 7 (memory).

## Slide 13 — Limitations · Discussion · ⏱ 1.5 min

**Takeaway:** FlowR *corrects* renderings — it cannot invent what was never seen; it depends on the initial reconstruction; static scenes only.

**Reveal sequence:**
▸ Reveal 1 — Headline + **(1) depends on the initial reconstruction:** the mapping is *wrong rendering → GT* — if stage 1 is poor, the result suffers.
▸ Reveal 2 — **(2) failure case (central):** regions visible in **no** source view → the model **does NOT hallucinate** → unobserved regions stay empty (the price of consistency; unlike pure diffusion).
▸ Reveal 3 — **(3) heuristic target-view selection** (B-spline/Fibonacci) → uncertainty / active view selection would be better.
▸ Reveal 4 — **(4) static scenes only:** dynamic objects → 3DGS artifacts; dynamic FlowR is open.

**Visual:** one failure-case image (unobserved region stays empty) + 4 concise bullets.
**Speaker note:** stress the tradeoff: the same design choice that prevents hallucination (Slide 6) forbids filling fully unobserved regions. Honest tension.
**Source:** paper Appendix A.2 (limitations) + Sec. 6.
